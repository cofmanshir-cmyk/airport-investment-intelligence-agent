# Design

This document explains how the Airport Investment Intelligence Agent is built, where an LLM is
used, and the tradeoffs behind those choices. For the score's formulas see
[METHODOLOGY.md](METHODOLOGY.md), and for sources and their limits see
[DATA_SOURCES.md](DATA_SOURCES.md).

## Architecture and data flow

```text
Public BTS / FAA data ──► src/pipeline.py ──► data/processed/*.parquet (versioned snapshot)
                                                        │
User question ──► LLM loop ──► tool call ──► src/tools.py ──► src/analytics.py, src/scoring.py
 (app.py / cli.py)  (agent.py,      ▲              │
                   gemini_agent.py) └── JSON result┘
                         │
                         ▼
          grounding + number checks ──► src/presentation.py ──► answer, tables, evidence
```

| Layer | File | Responsibility |
|---|---|---|
| Ingestion | `src/pipeline.py` | Fetches, validates and snapshots public data. Computes no metrics. |
| Calculations | `src/analytics.py`, `src/scoring.py` | Deterministic metrics and the Airport Opportunity Score. No LLM calls. |
| Tools | `src/tools.py` | Five tools with validated inputs. Each result carries definitions, sources and caveats. |
| LLM loops | `src/agent.py` (Anthropic), `src/gemini_agent.py` (Gemini) | Tool selection, conversation state and the explanation. |
| Grounding | `src/grounding.py` | Checks that a Gemini answer rests on data retrieved for the airports involved. |
| Presentation | `src/presentation.py` | Builds tables and evidence from tool output and hides flagged numbers. |
| Interfaces | `app.py` (Streamlit, Gemini), `src/cli.py` (terminal, Anthropic or Gemini) | Chat and code-generated evidence. |

The app reads only the processed snapshot, so it runs without raw files or live API calls.
`data/processed/manifest.json` records retrieval times, row counts and file hashes.

## Scoring

The Airport Opportunity Score is a preliminary screening proxy calculated entirely in Python:

- **11 weighted metrics** covering passenger growth, departure growth, load factor and
  acceleration, with weights totalling 100.
- **A fixed national peer group:** airports with at least 100,000 FAA CY2025 enplanements and
  all 11 metrics.
- **Normalisation:** each metric is clipped to the peer group's 5th and 95th percentiles,
  scaled from 0 to 100, then combined by weight.
- **Filters only change what's shown.** State and passenger filters never change a score or a
  national rank.
- **Missing data:** an airport missing any metric gets no score, with the reason. Nothing is
  estimated, and weights are never redistributed.

The score ranks airports for further review. It does not measure terminal capacity, unmet
demand, profitability or returns. Formulas, weights and warnings are in
[METHODOLOGY.md](METHODOLOGY.md).

## Where AI is used

| The LLM does | Deterministic Python does |
|---|---|
| Interprets the question and its follow-ups | Every calculation, score and rank |
| Chooses which tools to call and with what arguments | Input validation and airport code resolution |
| Writes the interpretation: conclusion, reasoning, cautions | Results tables, sources, definitions and caveats |
| Decides which result to feature | Grounding and number checks on the LLM's answer |

The tools are `rank_opportunity_score`, `rank_airports`, `compare_airports`,
`get_airport_profile` and `get_long_haul_share`. A system prompt (`src/agent.py`) sets the
analytical rules: keep congestion, demand proxies and capacity apart, never calculate or
reweight a score, never turn a score into an investment recommendation, and state the caution
that matters most.

Structured results tables, scores and ranks are generated by Python from tool output. The LLM may
cite those figures in its narrative, where the number check reviews them, but the tables and the
evidence section are built independently of the model's text.

## Grounding and uncertainty

- **Grounding check (Gemini):** an answer that names an airport, or states a figure, with no
  data retrieved in the conversation is discarded. The model then gets one further attempt that
  requires a tool call. If there's still no data, no answer is shown and the question can be
  asked again. General questions about definitions or methods need no tool.
- **Number check (both providers):** each number in an answer is compared with the tool results
  recorded in the conversation. Numbers with no match are shown as "[figure not verified]".
  This is a limited safeguard: it can't tell whether a figure belongs to the airport or measure
  it's attached to, and whole numbers often match something by chance.
- **Answers without a tool call:**
  - If the answer reuses airport data from an earlier turn, a note says so.
  - Otherwise a warning says no data result supports it.
- **Uncertainty from the tools:** results carry their own caveats, such as small-base warnings,
  sensitivity to the long-haul threshold, and lower and upper bounds where coverage is partial.
  The model is told to surface the caution that matters most.
- **Bounded tool use:** the Gemini loop allows three tool rounds per question, and its last
  round must answer from results already returned.

## Conversational follow-ups

- **Full history:** the conversation history goes back to the model, so earlier filters such as
  states, passenger thresholds and time windows carry forward unless the user changes them.
- **Main set:** the app tracks the main set of airports from the previous answer, meaning the
  shortlist or comparison the user saw. It passes them to the model as a note, so "those
  airports" resolves to exactly that set. The note never chooses a tool.
- **Reuse:** a follow-up can reuse earlier results when they fully answer it. A follow-up about
  an airport not yet retrieved needs a new tool call.
- **New Chat** clears the history, the main set and the retrieved-airport record.

## Key tradeoffs

| Choice | Benefit | Cost |
|---|---|---|
| Deterministic tools instead of LLM arithmetic | Reproducible, testable figures | Questions are limited to what the tools measure |
| Versioned snapshot instead of live API calls | Fast, offline-capable, reproducible | Data is as current as the last pipeline run |
| Fixed peer group and percentile clipping | Scores are stable under filters; outliers are capped | Scores are relative to this group and threshold only |
| Every metric treated as "higher is better" | One simple, transparent direction | Fast growth or a high load factor can also signal constraints |
| Cargo-inclusive departure metrics (35% of the score) | Uses the only departure series the API offers | Distortion at cargo-heavy airports |
| Grounding retry | Unsupported answers are withheld | One or two extra model calls when it triggers |
| Number check by value matching | Cheap and independent of the model | Can't attribute a figure to its airport or measure |
| Gemini model fallback, once per conversation | Survives model-specific outages | The rest of the conversation stays on the fallback model |

## Limitations

- **Not measured by any source used:** terminal capacity, gates, unmet demand, revenue and
  returns. Answers offer indirect signs only.
- **Passenger counts include connecting passengers,** so hub growth may reflect airline network
  decisions rather than local demand.
- **2022 was a recovery year,** which may inflate 3-year growth.
- **The long-haul route file covers January–July 2026 and US carriers only.** All-flight shares
  are therefore reported with bounds.
- **The T-100 summary was fetched from an API with no raw copy kept,** so its 2015 and 2022
  values can't be reconciled with an original file.

Full details are in [METHODOLOGY.md](METHODOLOGY.md) and [DATA_SOURCES.md](DATA_SOURCES.md).
